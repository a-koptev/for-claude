# Tracking и переходы между камерами

## Текущий режим

`Tracking.py` сейчас используется как интеграционный тест:

- YOLO + BoT-SORT дают локальные vehicle track ID и bbox;
- `CameraNetwork` загружает топологию;
- `CrossingDetector` определяет переходы между камерами;
- Re-ID/TrackletManager в текущем тесте отключён:
  `USE_TRACKLET_MANAGER = False`;
- одновременно тестируется OCR номерного знака по движущимся автомобилям.

Локальный numeric `track_id` не является глобальным ID автомобиля.

## Поток обработки кадра

1. Видео приводится к 1280×720.
2. Чистый кадр передаётся в YOLO/BoT-SORT.
3. Получаются bbox, confidence и локальные track ID.
4. `CrossingDetector` получает текущие bbox и вычисляет движение.
5. При подтверждённом переходе создаётся `TransitionEvent`.
6. Событие выводится в консоль и записывается в `transitions.log`.
7. Для движущихся track ID запускается OCR.
8. Результат OCR кэшируется по локальному track ID и отображается над bbox.
9. Линии переходов и визуальные подписи рисуются только на копии кадра.

## Фильтр движения

Для каждого track ID `CrossingDetector` хранит последнее смещение центра bbox.

Движение считается достаточным, если:

```
sqrt(dx² + dy²) >= TRANSITION_MIN_MOVE_PX
```

Сейчас `TRANSITION_MIN_MOVE_PX = 2.0`.

**Порядок принципиален:** сначала фильтр движения, затем проверка камер/линий. Стоящий автомобиль не должен генерировать переход.

## Геометрия перехода

После фильтра движения:

1. проверяется `MIN_MOTION_ALIGNMENT = 0.5`;
2. проверяется, что конечный отрезок линии находится между границами bbox по направлению движения;
3. учитываются реальные концы линии с допуском 30 px;
4. определяется `EXIT` или `ENTER` по направлению движения.

Повторное событие для `track_id + line_id` блокируется до выхода автомобиля из зоны линии. Разблокировка происходит после удаления от линии на 30 px в течение 5 кадров.

## OCR номерного знака

OCR пока тестируется **без Re-ID**.

Архитектура текущего вызова:

```
YOLO/BoT-SORT vehicle bbox
        ↓
кроп автомобиля
        ↓
YOLO detector номерного знака
        ↓
лучший plate bbox
        ↓
кроп номера
        ↓
PARSeq OCR
        ↓
PlateReading
```

Реализовано в `PlateOCRModule.py`.

### Когда запускается OCR

OCR запускается только для движущихся автомобилей:

```crossing_detector.is_moving(track_id)```

Периодичность по умолчанию — каждые 5 кадров:

```OCR_EVERY_N_FRAMES = 5
```

Это позволяет не тратить OCR на стоящие автомобили.

### Порог доверия

Результат принимается только если:

```
ocr_confidence >= OCR_MIN_CHAR_CONFIDENCE
```

Текущий порог — **0.70**.

Результат ниже 0.70:
- не показывается над bbox;
- не попадает в историю;
- не считается в debug-счётчике.

### Отображение

Над bbox показывается последний принятый результат:

```
ID 17 | A123BC77 OCR 91%
```

Если новый OCR не прошёл порог, старое принятое значение не заменяется плохим результатом.

## История OCR для отладки

Для каждого локального track ID ведётся:

```
ocr_history: dict[int, Counter[str]]
```

Каждое принятое распознавание увеличивает счётчик конкретного текста.

Пример:

```
[OCR] track=17 plate=A123BC77 conf=0.91 count=1 history={'A123BC77': 1}
[OCR] track=17 plate=A123BC77 conf=0.94 count=2 history={'A123BC77': 2}
[OCR] track=17 plate=A123BC78 conf=0.82 count=1 history={'A123BC77': 2, 'A123BC78': 1}
```

История очищается, когда локальный track ID исчезает. Это предотвращает смешивание данных, если BoT-SORT позже переиспользует numeric ID.

Сейчас счётчик использует **точное совпадение строки**. Параметр `OCR_LEVENSHTEIN_SIM_THRESHOLD = 0.80` зарезервирован для будущей группировки близких OCR-вариантов и пока не используется в этом счётчике.

## Конфигурация OCR

Основные параметры находятся в `Config.py`:

- `YOLO_PLATE_MODEL_PATH` — модель детектора номера;
- `OCR_MODEL_PATH` — checkpoint PARSeq OCR;
- `OCR_EVERY_N_FRAMES` — период OCR;
- `OCR_PLATE_CONF_THRESHOLD` — confidence plate detector;
- `OCR_PLATE_IOU_THRESHOLD` — IoU threshold plate detector;
- `OCR_PLATE_IMGSZ` — размер входа plate detector;
- `OCR_DEVICE` — `auto/cpu/cuda`;
- `OCR_BATCH_SIZE` — размер OCR batch;
- `OCR_MIN_CHAR_CONFIDENCE` — минимальная уверенность принятого OCR.

Пути моделей можно переопределить через:

```
PARKING_PLATE_YOLO_MODEL_PATH
PARKING_OCR_MODEL_PATH
PARKING_OCR_EVERY_N_FRAMES
PARKING_OCR_MIN_CHAR_CONFIDENCE
PARKING_OCR_DEVICE
PARKING_OCR_BATCH_SIZE
```

Ожидаемые пути по умолчанию:

```
Models/PlateRecognition/YOLOv8/best.pt
ocr_plate_number_soft/best_ocr.pt
```

## OCR package

`ocr_plate_number_soft/__init__.py` добавлен, поэтому каталог явно оформлен как Python package.

Локальные импорты checkpoint/pipeline поддерживают package-режим через относительные импорты.

`AspectBucketizer` и остальные OCR-компоненты являются локальным кодом проекта, а не внешним pip-пакетом.

## Архитектурное решение по идентификации

В итоговой системе OCR и Re-ID не конкурируют на равных:

1. если номер виден и OCR имеет высокую уверенность — номер является основным якорем идентичности;
2. надёжные OCR-связки могут обогащать Re-ID gallery embeddings этого автомобиля;
3. при сомнительном OCR — Re-ID используется как основной сигнал, OCR как дополнительное свидетельство;
4. если OCR отсутствует — используется Re-ID с учётом топологии/времени.

Это пока **архитектурное решение**: текущий код ещё не связывает OCR с Re-ID gallery и PostgreSQL.

## Граница сессии автомобиля

Векторы и идентичность автомобиля в дальнейшем должны жить только в рамках его нахождения в паркинге:

```
ВЪЕЗД → наблюдения/embeddings → межкамерный tracking → ВЫЕЗД
```

После выхода долгосрочный поиск старого автомобиля не требуется.
