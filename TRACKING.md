# Tracking и регистрация автомобилей

## Текущий режим

`Tracking.py` используется как интеграционный тест:

- YOLO + BoT-SORT дают локальные vehicle track ID и bbox;
- `CameraNetwork` загружает топологию;
- `CrossingDetector` определяет переходы между камерами;
- Re-ID/TrackletManager в текущем тесте может быть отключён;
- OCR номерного знака тестируется отдельно.

Локальный numeric `track_id` не является глобальным ID автомобиля.

---

# Регистрация автомобиля на въезде

## Цель

На въезде необходимо создать сущность автомобиля, которая начинается с надёжно распознанного номера на камере 1 и затем обогащается признаками Re-ID, собранными параллельно с трёх въездных камер.

Важный принцип:

> Регистрация автомобиля и локальный `track_id` — разные сущности.

`track_id` является текущим локальным идентификатором трекера конкретной камеры. Регистрация описывает сам автомобиль, который въехал в паркинг.

Предполагаемая структура регистрации:

```
VehicleRegistration
-------------------
registration_id
plate
entry_gate
created_at
camera_1_track_id
gallery/features
status
...
```

Конкретная схема PostgreSQL будет определена при реализации.

---

## Камера 1 — основной триггер регистрации

Камера 1 видит оба шлагбаума.

На ней создаются **две независимые линии регистрации**:

- линия левого шлагбаума;
- линия правого шлагбаума.

Простого триггера по попаданию bbox в зону использовать нельзя: за шлагбаумами находится обычная дорога, по которой постоянно проезжают посторонние автомобили.

Поэтому регистрация запускается только геометрическим событием:

```
нижний край bbox автомобиля
            ↓
      касается линии
            ↓
   определить LEFT / RIGHT
            ↓
    создать регистрацию
```

При срабатывании линии необходимо точно знать, какая линия была затронута. Это сохраняется как `entry_gate = LEFT/RIGHT` и в дальнейшем используется при работе с другими камерами.

В момент регистрации:

1. определяется локальный `track_id`;
2. берётся bbox автомобиля;
3. запускается извлечение номера;
4. запускается сбор Re-ID признаков;
5. создаётся сущность регистрации;
6. в ней сохраняются номер, время, шлагбаум и связанные данные;
7. для текущей регистрации в памяти формируется gallery embeddings.

### Важно

На этом этапе **не используется алгоритм определения движения автомобиля (EMA) для задач регистрации, OCR или Re-ID**.

То есть нельзя требовать, чтобы автомобиль считался движущимся, чтобы:

- снять номер;
- принять номер;
- получить Re-ID embedding;
- добавить embedding в gallery.

Регистрация должна срабатывать именно по геометрическому касанию линии.

---

# Линии переходов камер остаются рабочими

Отказ от EMA для регистрации **не означает отказа от существующей системы определения пересечения линий камер**.

`CrossingDetector` продолжает использоваться для определения переходов/выхода автомобиля из камеры.

Это принципиально необходимо для завершения сбора gallery.

Получается два разных механизма:

### Регистрация / сбор признаков

Не используют EMA:

```
bbox касается регистрационной линии
        ↓
trigger
        ↓
OCR + Re-ID
```

### Завершение наблюдения

Используется существующая логика пересечения линий перехода камер:

```
track пересёк линию выхода/перехода
        ↓
сбор gallery для этого наблюдения прекращается
```

Таким образом, EMA не должен блокировать получение номера или embedding, но существующий `CrossingDetector` продолжает управлять границами наблюдения.

---

# Gallery Re-ID

Для одного автомобиля не нужно сохранять embedding каждого кадра.

Используется механизм накопления разнообразной gallery.

Схема:

```
каждые N кадров
      ↓
получить crop автомобиля
      ↓
Re-ID model
      ↓
получить embedding
      ↓
сравнить с последним embedding
      ↓
similarity >= порога
       /             \\
     да               нет
     ↓                 ↓
не добавлять        добавить
                    в gallery
```

Рабочая идея текущего прототипа:

- embedding извлекается раз в `N` кадров;
- новый embedding сравнивается с последним элементом массива;
- если сходство **90% или выше**, embedding не добавляется;
- если сходство меньше 90%, embedding добавляется;
- массив gallery находится в памяти во время активной регистрации/наблюдения;
- затем gallery сохраняется в PostgreSQL одним массивом, чтобы не выполнять запрос в БД для каждого нового embedding.

Точный способ вычисления similarity и формат хранения будут сохранены/уточнены при реализации на основе существующего кода проекта.

### Зачем нужна gallery

Один embedding не должен считаться полным описанием автомобиля.

За время въезда автомобиль может иметь:

- разные углы;
- разные масштабы;
- частично закрытый кузов;
- разные видимые стороны;
- разные условия освещения.

Поэтому регистрация должна накапливать несколько достаточно разных качественных представлений.

---

# Горизонтальный flip

При извлечении Re-ID признаков допускается использовать исходный crop и его горизонтально отражённую версию.

Это является **синтетической аугментацией представления**, а не доказательством того, что физически была снята противоположная сторона автомобиля.

Механизм выбора количества таких embeddings и защита от избыточного увеличения gallery будут уточняться после тестирования.

---

# Зона съёма признаков

Зона съёма признаков и линия перехода — это разные понятия и не должны автоматически превращаться в одно правило.

Основная идея:

- **линия регистрации/trigger** определяет момент начала наблюдения автомобиля;
- после trigger можно некоторое время собирать Re-ID признаки;
- **линия перехода/выхода** определяет завершение соответствующего наблюдения;
- Re-ID не должен запускаться только потому, что EMA говорит, что автомобиль движется;
- наоборот, движение не должно блокировать получение OCR или embedding.

Для gallery важна не максимальная частота embeddings, а разнообразие наблюдений. Поэтому предпочтительно собирать признаки через заданный интервал кадров и отбрасывать слишком похожие embeddings.

При этом нельзя искусственно растягивать или задерживать обработку ради зоны съёма признаков: текущий pipeline должен обрабатывать последовательные кадры в естественном режиме.

---

# Камера 2 — скелет обработки

Камера 2 пока не решает задачу сопоставления автомобиля с камерой 1.

Главная задача текущего этапа — подготовить параллельный pipeline, который позже сможет получить связь:

```
VehicleRegistration
        ↕
Camera 2 local track
```

Сразу после регистрации автомобиля на камере 1 должна запускаться обработка потока камеры 2.

На этом этапе **не определяем**, какой именно track камеры 2 принадлежит зарегистрированному автомобилю.

Зоны и линии камеры 2 будут спроектированы отдельно после анализа реальной геометрии камеры.

---

# Камера 3

На камере 3 также создаётся линия-триггер.

Условие другое, чем на камере 1:

> регистрация наблюдения запускается, когда **верхний край bbox автомобиля касается нижней линии камеры 3**.

Это позволяет отсечь автомобили, которые просто проходят/проезжают мимо камеры 3 и не приехали через наши шлагбаумы.

При срабатывании:

```
верх bbox
    ↓
касается нижней линии камеры 3
    ↓
найден локальный track
    ↓
начинается сбор Re-ID gallery
```

На камере 3 также можно временно тестировать OCR номера. Если качество окажется недостаточным или OCR будет мешать основному pipeline, его можно отключить без изменения основной архитектуры.

---

# Камера 3 — автомобиль может не попасть на неё

Важно учитывать реальную геометрию въезда.

Автомобиль с любого из двух шлагбаумов может уехать влево. В таком случае он может вообще не попасть на камеру 3.

Поэтому камера 3 не должна считаться обязательным этапом регистрации каждого автомобиля.

Система запускает обработку **всех трёх потоков одновременно**.

Если зарегистрированный/искомый автомобиль или автомобили с камеры 2 уходят в сторону камеры 9, это означает, что для соответствующего сценария камера 3 больше не нужна.

В этом событии сбор признаков на камере 3 для соответствующих активных регистраций/наблюдений прекращается.

То есть:

```
Camera 2
   ↓
автомобиль ушёл в сторону Camera 9
   ↓
Camera 3 для этого сценария больше не ожидается
   ↓
прекратить сбор gallery на Camera 3
```

Конкретный механизм определения соответствующего перехода будет реализован на следующем этапе после определения зон/сопоставления камер.

---

# Параллельная обработка трёх камер

Для тестирования регистрационной системы все три потока должны запускаться одновременно:

```
                    ┌── Camera 1
                    │    registration
                    │    OCR + Re-ID
                    │
Realtime processing ├── Camera 2
                    │    candidate processing
                    │    Re-ID / OCR
                    │
                    └── Camera 3
                         line trigger
                         Re-ID / OCR
```

Сбор признаков на всех активных камерах происходит параллельно.

Нельзя строить pipeline как:

```
Camera 1 закончила
    ↓
Camera 2
    ↓
Camera 3
```

Потоки должны существовать одновременно, потому что реальные автомобили находятся в разных камерах одновременно.

---

# Особый сценарий Camera 4 → Camera 3 / Camera 2

В топологии есть место, где после выхода автомобиля из камеры 4 его имеет смысл искать сразу на камерах 3 и 2.

Это **локальное специальное правило**, а не новая глобальная связь топологии.

Предполагаемое поведение:

```
Camera 4
   │
   │ exit
   ▼
┌───────────────┐
│ начать поиск  │
│ автомобиля    │
└───────────────┘
      │
      ├────────→ Camera 3
      │
      └────────→ Camera 2
```

Идея:

- камеры 3 и 2 могут проверяться параллельно;
- камера 3 может иметь приоритет при выборе подтверждения;
- не требуется искусственно добавлять переход `Camera 3 → Camera 2`;
- это именно поиск одного автомобиля в нескольких возможных камерах;
- числовые `track_id` нельзя сравнивать между камерами напрямую, поскольку они локальны для каждой камеры.

Эта логика **пока не реализуется**. Она зафиксирована как будущий сценарий.

---

# Candidate handoff — будущая идея

Во время обсуждения межкамерного поиска возникла проблема с жёстким правилом:

```
пересёк линию
    ↓
забыть старую камеру
    ↓
искать только в следующей камере
```

Так делать нельзя.

Причина особенно важна для парковки: автомобиль может парковаться задним ходом и несколько раз двигаться вперёд/назад. В результате он способен повторно пересекать линии, не покидая фактически текущую область наблюдения.

Поэтому переход по линии должен считаться **наблюдением/сигналом для поиска**, а не окончательным подтверждением смены камеры.

Предлагаемая будущая схема:

```
Текущая камера
      │
      │ transition event
      ▼
candidate camera
      │
      ├── Re-ID подтверждён ──→ подтвердить новую камеру
      │
      └── Re-ID не подтверждён → не терять старое наблюдение
```

То есть вводится двухуровневая модель:

### 1. Transition event

`CrossingDetector` сообщает:

> автомобиль пересёк линию, поэтому возможен переход в другую камеру.

### 2. Candidate handoff

Система временно создаёт кандидата на целевой камере:

```
CURRENT
  camera 5

CANDIDATE
  camera 6
```

Старая камера при этом **не забывается сразу**.

Только после достаточно уверенного Re-ID сопоставления новая камера становится подтверждённым продолжением наблюдения.

Это позволяет пережить:

- ложные пересечения;
- повторные пересечения при парковке;
- движение задним ходом;
- перекрытия;
- временное отсутствие автомобиля на предполагаемой целевой камере;
- неоднозначность между несколькими соседними камерами.

Если подтверждения нет, исходная связь не должна уничтожаться только из-за события пересечения линии.

---

# Candidate handoff для Camera 4 → Camera 3 / Camera 2

Специальный сценарий камеры 4 хорошо укладывается в ту же модель:

```
                 Camera 4
                    │
                    │ exit
                    ▼
             active vehicle
               /          \\
              /            \\
       candidate          candidate
       Camera 3           Camera 2
           │                  │
           └──── Re-ID ──────┘
                    ↓
          подтверждённая камера
```

При этом:

- поиск на камерах 3 и 2 может идти параллельно;
- камера 3 может быть предпочтительной;
- старая камера 4 остаётся валидной до подтверждения;
- если ни одна целевая камера не подтвердила автомобиль, нельзя считать, что автомобиль потерян только из-за пересечения линии;
- после подтверждения одной камеры поиск в остальных кандидатах можно остановить или перевести в низкий приоритет.

Это **концептуальное решение на будущее**, а не текущая реализация.

---

# Почему нельзя жёстко забывать предыдущую камеру

Сценарий парковки принципиально отличается от обычного линейного движения:

```
камера A
   ↓
камера B
   ↓
камера C
```

На парковке автомобиль может:

```
вперёд
  ↓
назад
  ↓
вперёд
  ↓
назад
```

и при этом оставаться в одной области парковки.

Поэтому:

> пересечение линии ≠ гарантированная смена активной камеры.

Линия даёт геометрический факт. Re-ID должен подтверждать, что наблюдение действительно относится к тому же автомобилю на другой камере.

Это особенно важно перед реализацией глобального ID.

---

# Граница сбора gallery

Для каждой камеры сбор признаков начинается после соответствующего trigger-события и продолжается до окончания наблюдения за автомобилем.

Общее правило:

```
trigger
  ↓
начало сбора gallery
  ↓
Re-ID embeddings каждые N кадров
  ↓
фильтрация похожих embeddings
  ↓
пересечение существующей линии перехода / выход из наблюдаемой зоны
  ↓
остановка сбора gallery
```

При этом существующая система переходов между камерами не удаляется и не заменяется новой системой регистрации.

Важно: будущий `candidate handoff` должен позволять отделить **окончание локального наблюдения** от **подтверждения межкамерного перехода**. Сам факт перехода не должен автоматически уничтожать источник Re-ID поиска.

---

# Связь Registration, Track и Gallery

Нужно разделять три уровня:

### Registration

Факт въезда конкретного автомобиля:

```
registration_id
plate
entry_gate
timestamp
...
```

### Local Track

Временный ID BoT-SORT внутри конкретной камеры:

```
Camera 1 → track_id
Camera 2 → track_id
Camera 3 → track_id
```

Один и тот же numeric `track_id` нельзя считать глобальной идентичностью автомобиля.

### Gallery

Набор Re-ID embeddings, накопленных для автомобиля:

```
gallery = [
    embedding_1,
    embedding_2,
    embedding_3,
    ...
]
```

В дальнейшем gallery будет использоваться для сопоставления автомобиля между камерами и восстановления связи после возможной смены/потери локального track ID.

---

# Что пока НЕ реализуем

На этом этапе намеренно не решаются:

1. сопоставление автомобиля камеры 1 с конкретным track камеры 2;
2. зоны/линии камеры 2 для определения конкретного автомобиля;
3. полноценная межкамерная Re-ID идентификация;
4. EMA/direction detection для регистрации, OCR или Re-ID;
5. определение направления движения автомобиля как отдельный сигнал;
6. сложная логика восстановления track после перекрытия;
7. окончательная схема PostgreSQL/pgvector;
8. финальная логика глобального ID;
9. окончательная оптимизация gallery;
10. маршрутизация по всей топологии паркинга;
11. **candidate handoff и подтверждение межкамерного перехода через Re-ID**;
12. **специальный параллельный поиск Camera 4 → Camera 3 / Camera 2**.

Эти идеи зафиксированы как следующие этапы, но пока не должны менять рабочую логику переходов.

---

# OCR

На боковой и задней камерах OCR номера пока допускается оставить включённым в тестовом режиме.

При этом:

- камера 1 — основной и наиболее надёжный источник номера;
- камера 2/3 — дополнительные экспериментальные источники;
- плохое OCR на камере 2/3 не должно ломать Re-ID gallery;
- OCR не должен требовать подтверждения движения автомобиля через EMA.

---

# Realtime processing

Три камеры должны обрабатываться параллельно.

При этом нельзя искусственно синхронизировать нейросети через фиксированные `sleep()` или задержки, потому что в один момент времени могут одновременно запускаться:

- YOLO vehicle tracking;
- Re-ID;
- YOLO plate detector;
- OCR.

Это может создавать пики нагрузки GPU.

Пока не вводится отдельная стратегия frame dropping/latest-frame: для текущего теста важно сохранить последовательность обработки кадров и сначала проверить фактическое поведение системы.

Realtime-захват и стратегия управления очередью кадров будут отдельно уточнены после тестирования.

---

# Следующий этап

После реализации данного скелета следующим этапом будет решение основной задачи камеры 2:

```
Camera 1
  ↓
регистрация по LEFT/RIGHT линии
  ↓
plate + registration + gallery
  ↓
Camera 2
  ↓
определить, какой local track
соответствует зарегистрированному автомобилю
  ↓
стабильно сопровождать именно этот автомобиль
  ↓
если track потерян/переключился —
восстановить связь через Re-ID и другие признаки
```

Главная цель — не привязать автомобиль навсегда к одному numeric `track_id`, а поддерживать устойчивую связь:

```
VehicleRegistration
        ↕
   current local track
        ↕
      gallery
```

Это позволит переживать потерю/переключение локального track ID без потери идентичности автомобиля.
