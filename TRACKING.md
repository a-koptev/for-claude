# Tracking и переходы между камерами

## Текущий режим

`Tracking.py` сейчас используется как интеграционный тест:

- YOLO + BoT-SORT дают локальные vehicle track ID и bbox;
- `CameraNetwork` загружает топологию;
- `CrossingDetector` определяет переходы между камерами;
- Re-ID/TrackletManager в текущем тесте отключён:
  `USE_TRACKLET_MANAGER = False`;
- одновременно тестируется OCR номерного знака по движущимся автомобилям.

Локальный numeric `track_id` не является глобальным ID автомобиля.

## Поток обработки кадра

1. Видео приводится к 1280×720.
2. Чистый кадр передаётся в YOLO/BoT-SORT.
3. Получаются bbox, confidence и локальные track ID.
4. `CrossingDetector` получает текущие bbox и вычисляет движение.
5. При подтверждённом переходе создаётся `TransitionEvent`.
6. Событие выводится в консоль и записывается в `transitions.log`.
7. Для движущихся track ID запускается OCR.
8. Результат OCR кэшируется по локальному track ID и отображается над bbox.
9. Линии переходов и визуальные подписи рисуются только на копии кадра.

## Фильтр движения

Для каждого track ID `CrossingDetector` хранит последнее смещение центра bbox.

Движение считается достаточным, если:

```
sqrt(dx² + dy²) >= TRANSITION_MIN_MOVE_PX
```

Сейчас `TRANSITION_MIN_MOVE_PX = 2.0`.

**Порядок принципиален:** сначала фильтр движения, затем проверка камер/линий. Стоящий автомобиль не должен генерировать переход.

## Геометрия перехода

После фильтра движения:

1. проверяется `MIN_MOTION_ALIGNMENT = 0.5`;
2. проверяется, что конечный отрезок линии находится между границами bbox по направлению движения;
3. учитываются реальные концы линии с допуском 30 px;
4. определяется `EXIT` или `ENTER` по направлению движения.

Повторное событие для `track_id + line_id` блокируется до выхода автомобиля из зоны линии. Разблокировка происходит после удаления от линии на 30 px в течение 5 кадров.

## OCR номерного знака

OCR пока тестируется **без Re-ID**.

Архитектура текущего вызова:

```
YOLO/BoT-SORT vehicle bbox
        ↓
кроп автомобиля
        ↓
YOLO detector номерного знака
        ↓
лучший plate bbox
        ↓
кроп номера
        ↓
PARSeq OCR
        ↓
PlateReading
```

Реализовано в `PlateOCRModule.py`.

### Когда запускается OCR

OCR запускается только для движущихся автомобилей:

```crossing_detector.is_moving(track_id)```

Периодичность по умолчанию — каждые 5 кадров:

```OCR_EVERY_N_FRAMES = 5
```

Это позволяет не тратить OCR на стоящие автомобили.

### Порог доверия

Результат принимается только если:

```
ocr_confidence >= OCR_MIN_CHAR_CONFIDENCE
```

Текущий порог — **0.70**.

Результат ниже 0.70:
- не показывается над bbox;
- не попадает в историю;
- не считается в debug-счётчике.

### Отображение

Над bbox показывается последний принятый результат:

```
ID 17 | A123BC77 OCR 91%
```

Если новый OCR не прошёл порог, старое принятое значение не заменяется плохим результатом.

## История OCR для отладки

Для каждого локального track ID ведётся:

```
ocr_history: dict[int, Counter[str]]
```

Каждое принятое распознавание увеличивает счётчик конкретного текста.

Пример:

```
[OCR] track=17 plate=A123BC77 conf=0.91 count=1 history={'A123BC77': 1}
[OCR] track=17 plate=A123BC77 conf=0.94 count=2 history={'A123BC77': 2}
[OCR] track=17 plate=A123BC78 conf=0.82 count=1 history={'A123BC77': 2, 'A123BC78': 1}
```

История очищается, когда локальный track ID исчезает. Это предотвращает смешивание данных, если BoT-SORT позже переиспользует numeric ID.

Сейчас счётчик использует **точное совпадение строки**. Параметр `OCR_LEVENSHTEIN_SIM_THRESHOLD = 0.80` зарезервирован для будущей группировки близких OCR-вариантов и пока не используется в этом счётчике.

## Конфигурация OCR

Основные параметры находятся в `Config.py`:

- `YOLO_PLATE_MODEL_PATH` — модель детектора номера;
- `OCR_MODEL_PATH` — checkpoint PARSeq OCR;
- `OCR_EVERY_N_FRAMES` — период OCR;
- `OCR_PLATE_CONF_THRESHOLD` — confidence plate detector;
- `OCR_PLATE_IOU_THRESHOLD` — IoU threshold plate detector;
- `OCR_PLATE_IMGSZ` — размер входа plate detector;
- `OCR_DEVICE` — `auto/cpu/cuda`;
- `OCR_BATCH_SIZE` — размер OCR batch;
- `OCR_MIN_CHAR_CONFIDENCE` — минимальная уверенность принятого OCR.

Пути моделей можно переопределить через:

```
PARKING_PLATE_YOLO_MODEL_PATH
PARKING_OCR_MODEL_PATH
PARKING_OCR_EVERY_N_FRAMES
PARKING_OCR_MIN_CHAR_CONFIDENCE
PARKING_OCR_DEVICE
PARKING_OCR_BATCH_SIZE
```

Ожидаемые пути по умолчанию:

```
Models/PlateRecognition/YOLOv8/best.pt
ocr_plate_number_soft/best_ocr.pt
```

## OCR package

`ocr_plate_number_soft/__init__.py` добавлен, поэтому каталог явно оформлен как Python package.

Локальные импорты checkpoint/pipeline поддерживают package-режим через относительные импорты.

`AspectBucketizer` и остальные OCR-компоненты являются локальным кодом проекта, а не внешним pip-пакетом.

## Архитектурное решение по идентификации

В итоговой системе OCR и Re-ID не конкурируют на равных:

1. если номер виден и OCR имеет высокую уверенность — номер является основным якорем идентичности;
2. надёжные OCR-связки могут обогащать Re-ID gallery embeddings этого автомобиля;
3. при сомнительном OCR — Re-ID используется как основной сигнал, OCR как дополнительное свидетельство;
4. если OCR отсутствует — используется Re-ID с учётом топологии/времени.

Это пока **архитектурное решение**: текущий код ещё не связывает OCR с Re-ID gallery и PostgreSQL.

## Граница сессии автомобиля

Векторы и идентичность автомобиля в дальнейшем должны жить только в рамках его нахождения в паркинге:

```
ВЪЕЗД → наблюдения/embeddings → межкамерный tracking → ВЫЕЗД
```

После выхода долгосрочный поиск старого автомобиля не требуется.

## Следующий этап

После стабилизации текущего теста:

1. добавить Re-ID;
2. ограничивать Re-ID-кандидатов допустимыми соседними камерами из topology;
3. использовать временное окно между `EXIT` и появлением на соседней камере;
4. связать надёжный OCR с глобальным ID автомобиля;
5. хранить session/plate/confidence/embeddings/events в PostgreSQL + pgvector;
6. сделать динамическую Re-ID gallery, пополняемую только надёжными связями;
7. предусмотреть перепривязку глобального ID, а не жёсткую фиксацию ID за автомобилем.


# Realtime architecture — обязательное требование

Realtime является обязательным требованием итоговой системы. Tracking.py не должен искусственно замедляться до FPS исходного видео через sleep() или cv2.waitKey(1000 / FPS). Это было бы неверно для реальной камеры/RTSP.

## Главный принцип

При перегрузке система не должна накапливать старые кадры и уходить всё дальше в прошлое. Нужно обрабатывать максимально свежий кадр, а устаревшие промежуточные кадры отбрасывать.

Целевая схема:

```text
CAMERA / RTSP
      ↓
capture worker
      ↓
bounded latest-frame buffer (предпочтительно size=1)
      ↓
YOLO + BoT-SORT tracking
      ↓
tracking state
   ↙       ↘
 ReID      OCR
             ↓
       plate YOLO → OCR
```

Если камера выдаёт 30 FPS (примерно один кадр каждые 33 ms), а обработка занимает 90 ms на кадр, последовательная обработка всех кадров физически даёт около 11 FPS. Нельзя в таком случае бесконечно складывать кадры в очередь: latency будет расти. Правильное поведение — пропускать устаревшие кадры и продолжать с актуальным состоянием камеры.

## OCR/Re-ID не должны блокировать realtime tracking

Тяжёлые операции должны выполняться с контролируемой частотой или асинхронно:

- YOLO/BoT-SORT — на каждом доступном актуальном кадре, насколько позволяет производительность;
- Re-ID — каждые N кадров или по событию;
- plate detector — с контролируемой периодичностью / trigger;
- OCR — только после хорошего обнаружения номера.

Главный tracking loop не должен ждать бесконечную очередь OCR/Re-ID.

## Метрики производительности

Нужно измерять:

- source/arrival FPS;
- processing FPS;
- latency;
- время GPU inference;
- количество dropped frames.

Пример:

```text
[PERF] source=30.0 FPS processing=28.4 FPS latency=31 ms dropped=12
```

При перегрузке должно быть видно, например:

```text
[PERF] source=30 FPS processing=12 FPS latency=450 ms
```

CAP_PROP_FPS можно использовать для диагностики/метаданных, но нельзя использовать как throttle. Для live stream полезнее измерять реальное время поступления кадров через performance timestamps.

## Последствие drop frames для движения

Текущий CrossingDetector считает движение между обработанными кадрами:

```text
dx = current_center.x - previous_center.x
dy = current_center.y - previous_center.y
```

и использует TRANSITION_MIN_MOVE_PX = 2.0. После перехода на latest-frame/drop-frame архитектуру одинаковое количество пикселей между двумя обработанными кадрами может соответствовать разному времени. Поэтому следующим этапом после стабилизации realtime capture нужно перевести движение на timestamp-aware модель:

```text
dx / dt
dy / dt
или pixels/sec
```

То же касается текущих frame-based параметров:

- OCR_EVERY_N_FRAMES = 5;
- TRANSITION_RELEASE_FRAMES = 5;
- TRANSITION_FORGET_FRAMES = 150.

В дальнейшем их желательно заменить на интервалы в секундах / timestamp scheduling.

**Важно:** не менять эти параметры вслепую до внедрения realtime capture и измерения фактической производительности.

## Следующий технический этап

При реализации realtime:

1. добавить отдельный capture worker/thread;
2. сделать bounded latest-frame buffer;
3. брать самый свежий кадр;
4. отбрасывать stale frames;
5. не добавлять sleep()/FPS throttle;
6. сохранить текущие YOLO + BoT-SORT + topology + OCR;
7. добавить performance metrics;
8. после стабилизации перейти на timestamp-based movement/cadence.


## Реализация realtime capture

В Tracking.py обработка отделена от захвата видео через RealtimeFrameSource.

### Правила

- VideoCapture работает в отдельном capture-потоке.
- Буфер содержит только **последний доступный кадр** (latest-frame, фактически очередь размера 1).
- Если inference не успевает за источником, старые промежуточные кадры отбрасываются, а не накапливаются в очереди.
- cv2.waitKey(1) используется только для обработки окна и клавиатуры; он не является FPS-throttle.
- Для локального файла pacing выполняется внутри capture-потока по заявленному FPS источника. Это имитирует временную шкалу камеры, но не замедляет нейросети.
- Для live/RTSP кадры забираются по мере их поступления.

### Метрики

RealtimeFrameSource периодически печатает:

    [PERF] source=30.0 FPS processing=28.4 FPS latency=31 ms dropped=12 captured=100 processed=88

где:

- source — фактическая скорость поступления кадров в capture worker;
- processing — фактическая скорость обработки кадров основным циклом;
- latency — среднее время от публикации кадра capture worker до обработки;
- dropped — сколько кадров было заменено более свежими кадрами до обработки;
- captured/processed — накопленные счётчики.

CAP_PROP_FPS используется только для диагностики и временной шкалы локального файла. Он не используется для искусственного торможения inference.

### Почему это важно

Если источник даёт 30 FPS, а обработка временно занимает 90 ms на кадр, система не должна строить очередь из старых кадров. Она будет обрабатывать свежие кадры, а промежуточные потеряет. Это ограничивает рост latency.

Текущие пороги TRANSITION_* и OCR_EVERY_N_FRAMES пока не переводятся на секунды: сначала нужно получить реальные source/processing/latency/dropped на тестовых видео. Следующий этап — timestamp-aware движение (dx/dt, dy/dt) и time-based cadence для OCR/transition timers.
