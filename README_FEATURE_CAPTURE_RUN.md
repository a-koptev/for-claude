# Запуск сбора признаков с триггером

## Быстрый запуск

1. В `Config.py` заполните `Config.CAMERA_VIDEO_PATHS` для камер 1–3. Путь может быть абсолютным или относительным к корню проекта. Можно также задать переменные окружения `PARKING_CAMERA_1_VIDEO` … `PARKING_CAMERA_9_VIDEO`.
2. Проверьте полигоны в `feature_zones.yaml` и линии переходов в `topology.yaml`.
3. Запустите из корня проекта:

   ```bash
   python run_feature_capture.py
   ```

4. До срабатывания триггера окно показывает камеру 1. Машина должна попасть контрольной точкой bbox в одну из зон LEFT/RIGHT. После активации окно переключается на раскладку камер 1–3.
5. Нажмите `Q` или `Esc`, чтобы остановить программу.

## Конфигурация камер

В `Config.py` есть словарь `CAMERA_VIDEO_PATHS` с ключами 1–9. Для камер 4–9 пути можно заполнить сейчас, но этот сценарий сбора признаков их не открывает: Re-ID сбор по-прежнему ограничен камерами 1–3. Пустой путь означает, что источник не задан.

## Как работает триггер

- Используется YOLO + существующий BoT-SORT tracker.
- До триггера анализируется только камера 1; на экране видны полигоны и локальные ID.
- Триггер срабатывает, когда контрольная точка bbox нового локального трека входит в LEFT или RIGHT зону камеры 1.
- После активации галерея этого трека продолжает собирать признаки за пределами полигона, пока трек видим или пока галерея не закрыта.
- На каждой выборке оригинальный crop и его горизонтальное отражение передаются в один вызов экстрактора. Сохраняются два отдельных L2-нормализованных эмбеддинга.
- Новый оригинальный эмбеддинг сравнивается с последним принятым оригиналом. При cosine similarity >= 0.90 пара original/flip отклоняется как почти дубликат.
- Под рамкой трека отображаются `cos dist` и `sim`, когда доступно сравнение.

## Завершение и мок БД

На камере 2 существующее событие пересечения линии с ролью EXIT закрывает локальную галерею. Для неё выводится мок записи с:
- `car_id` вида `MOCK-CAR-0001`;
- количеством original features;
- количеством flipped features;
- общим количеством векторов.

Это только демонстрация формата записи. Реальное подключение к БД не выполняется. В текущей версии мок относится к локальной галерее трека камеры 2: межкамерная привязка галерей к одной физической машине ещё не подключена, поэтому счётчик не следует трактовать как суммарное число признаков машины по всем камерам. Для галерей камер 1 и 3 мок-запись не создаётся.

Если EXIT на камере 2 не произошёл до конца видео или ручной остановки, незакрытые галереи попадут в JSON-отчёт как оставшиеся при завершении, но не будут отправлены даже в мок БД.

## Выходные файлы

- `feature_capture_run.log` — журнал триггера, переходов, завершения галерей и мок-записей.
- `feature_capture_run_report.json` — счётчики кадров, принятых/отклонённых образцов, переходы, мок-записи и незакрытые галереи.

## Ограничения текущего этапа

- Камеры 4–9 пока только конфигурируются; этот runner не обрабатывает их видео и не извлекает по ним признаки.
- FIFO-привязка между камерами 1 и 2 и распознавание «зарегистрированный въезд / посторонний автомобиль» не подключены.
- `car_id` генерируется заглушкой, а не извлекается из БД или OCR.
- OCR вызывается для активных треков сбора признаков; реальная запись в БД не выполняется.
- Сценарий рассчитан на локальные видеофайлы для проверки потока. Входы камер читаются параллельно в режиме ожидания триггера, чтобы приблизительно сохранять временное соответствие клипов.


## Номер автомобиля и журнал трека

Для активных треков сбора включается существующий OCR-стек: детектор номера YOLO и распознаватель PARSeq. OCR запускается раз в \`Config.OCR_EVERY_N_FRAMES\` кадров; результаты с уверенностью ниже \`Config.OCR_MIN_CHAR_CONFIDENCE\` не учитываются.

Для каждого локального трека и камеры накапливается словарь вида \`{номер: [уверенности OCR]}\`. OCR-модуль сам нормализует кириллические буквы, визуально совпадающие с латинскими, к латинице и удаляет разделители. Runner не содержит таблицу символов и получает уже нормализованный текст из `PlateOCRModule`. Победитель выбирается по **максимальной средней уверенности**; при равной средней уверенности побеждает вариант с большим числом наблюдений. Это соответствует схеме из примера, но важно помнить: средняя уверенность — эвристика, а не калиброванная вероятность правильности номера.

Номер и средняя уверенность показываются под треком. При событии EXIT в журнал пишется одна короткая строка с камерой/track ID, выбранным номером, числом сохранённых векторов, пересечённой линией и следующей камерой. В журнал не выводятся подробности каждого OCR-вызова или каждого кадра.

Пример:

\`\`\`text
track=2:17 plate=K552TC124 plate_conf=0.980 features=24 (original=12, flipped=12) crossed_line=2 next_camera=4
\`\`\`

Если ни одно чтение не прошло порог OCR, номер будет \`UNKNOWN\`. Мок-запись для камеры 2 включает выбранный номер и его среднюю уверенность, но реальная запись в БД по-прежнему не выполняется.
